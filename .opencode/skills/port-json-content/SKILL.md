# Пакетный перенос JSON-контента в вики

## Расположение файлов (пути от корня репозитория bc-rag)

**Все скрипты запускаются ТОЛЬКО через `uv run python`** — зависимости (pyyaml и др.) видны только в uv-managed окружении.

- Словарь терминов: `.opencode/skills/wh40k-to-fantasy/dictionary.yaml`
- Загрузчик JSON-записей: `ingest/json_source.py`
- Маппинг категорий на файлы вики: `.opencode/skills/port-json-content/target_map.yaml`
- Политика категорий (include/exclude, режим адаптации): `.opencode/skills/port-json-content/category_policy.yaml`
- Очередь переноса: `.opencode/skills/port-json-content/json_porting_queue.yaml`
- Исходный JSON с контентом книги: `data/core_rules/merged.json`
- Целевая вики: `../pathfinder-crusade-wiki/`
- Скрипт точечного поиска одной записи:
  `uv run python .opencode/skills/port-json-content/scripts/find_entry.py <json> <category> <key>`
- Скрипт пакетной подготовки черновика:
  `uv run python .opencode/skills/port-json-content/scripts/batch_prepare.py <json> <category> [--target <файл>]`
- Вспомогательные скрипты (обычно запускает человек, не агент):
  `scripts/list_categories.py`, `scripts/generate_json_queue.py`, `scripts/update_queue_status.py`, `scripts/reset_queue_status.py`

## Жёсткие правила
- **НИКОГДА не редактировать файлы в `data/core_rules/`** — read-only эталон.
- Переносить только в файлы вики (`../pathfinder-crusade-wiki/`), никогда наоборот.
- Не переписывать существующий контент вики — только **добавлять**. Если раздел с тем же заголовком уже есть — расширить или пропустить, если он уже полный.
- Система "поклонение богу меняет цену/доступность таланта или навыка" в вики не используется. Поля `god`, `rivalGod`, `alliedTo`, `hostileTo` из JSON **никогда не переносятся** — ни как есть, ни в адаптированном виде. Из группирующих полей остаются только `aptitude` (→ "Скл.:"), `level`, `requirements`.
- Никогда не создавать новые целевые файлы самостоятельно — все целевые файлы созданы человеком заранее и прописаны в `target_map.yaml`. Нет цели у записи — пропускать (`needs_target`), не выдумывать файл.
- Для пакетной обработки использовать готовый `scripts/batch_prepare.py`, не писать новые вспомогательные скрипты на лету.
- Агент никогда не выполняет `git commit`. Изменения остаются в рабочем дереве.
- **`description` переносится ПОЛНОСТЬЮ, без сокращения или пересказа.** Разрешена только замена терминов по словарю — все предложения, порядок изложения, механические детали должны сохраниться один в один по смыслу и количеству информации. Автосокращение — такая же ошибка, как потеря числового значения в требованиях.
- **Перенос строки внутри блока оформляется двумя пробелами в конце строки перед `\n`** (markdown hard break), как во всей остальной вики.

## Предусловие
`json_porting_queue.yaml` должен существовать и быть сгенерирован из актуального `target_map.yaml` (это делает человек через `scripts/generate_json_queue.py` — агент этот шаг не выполняет самостоятельно, `target_map.yaml` заполняется вручную).

## Пакетная обработка
Для загрузки записей категории (или одного target-файла) используется `scripts/batch_prepare.py`, а не написание нового скрипта на лету и не последовательные вызовы `find_entry.py` по одной записи:

    uv run python scripts/batch_prepare.py <json> <category> [--target <файл>]

Скрипт выдаёт YAML, сгруппированный по `target`, с сырыми (НЕ адаптированными) полями под шаблон категории — только записи со статусом `not_started` и с заполненным `target`. `find_entry.py` — для точечной проверки одной записи (разбор `#Review`, спорный случай), не для основного потока.

## Шаги на один целевой файл

1. Получить черновик через `batch_prepare.py` для нужной категории (или конкретного `--target`, если ограничение задано в промпте).
2. Обрабатывать черновик **файл за файлом** (один `target` — один блок работы), не вперемешку.
3. Для каждой записи внутри текущего target-файла:
   a. Адаптировать текстовые поля (`description` и т.п.) по словарю — инвариантные термины точной заменой, склоняемые — с согласованием падежа/числа. Длина адаптированного текста должна быть сопоставима с оригиналом. Перед вставкой сверить финальный `description` с исходным `raw['description']` из черновика — если пропущено предложение или абзац, вернуть их назад.
   b. Не переносить `god`, `rivalGod`, `alliedTo`, `hostileTo` ни в каком виде.
   c. Оставить как есть (без адаптации, кроме числовых опечаток): `level`, `xpCost`, `requirements`, `action`, `range`, `sustain`, `aptitude`.
   d. Проверить на Chaos-маркеры (см. ниже) — при необходимости добавить `#Review` с кратким пояснением.
   e. Собрать финальный блок по шаблону категории (см. "Шаблоны вывода").
4. Вставить все собранные блоки в файл `target`, в логичное место (рядом с похожими записями, не в конец без разбора).
5. Оставить изменения незакоммиченными. Можно вывести короткую сводку после завершения файла: сколько записей обработано, есть ли `#Review`.
6. Обновить статус всех обработанных записей в `json_porting_queue.yaml`: `done` или `needs_review`. Эти изменения тоже остаются незакоммиченными.
7. Перейти к следующему target-файлу. Повторять автономно до отсутствия записей `not_started` в рамках текущего прогона — подтверждение на каждую единицу не требуется.

## Chaos-маркеры (проверка независимо от категории)
Ни `category`, ни `entryType`, ни `discipline` не гарантируют отсутствие Chaos-специфичного контента. На шаге 3d проверять текст на прямые маркеры:
- упоминания конкретных Chaos-богов (Tzeentch/Nurgle/Khorne/Slaanesh или русских имён) или эпитетов;
- ритуальная атрибутика поклонения (иконы, восьмеричная звезда, жертвенные символы);
- Cor (Порча) как механика;
- глубокий Imperium-лор (конкретные примархи, Империум, техно-физиология вроде "Второе Сердце космодесантника").

Найден маркер — не "нейтрализовывать" самостоятельно (например, просто заменить "Хаос" на нейтральное слово) — вставлять с `#Review` и коротким пояснением, что именно завязано на Chaos/Imperium-лор.

### Автоматический #Review для WH40k-специфичных категорий талантов
Записи с `talents.category` из списка: `Geneseed`, `Skitarii`, `Mechanicum`, `Technomystic` — если для них появится `target` в `target_map.yaml` (сейчас `null`) — помечаются `#Review` на КАЖДОЙ записи независимо от того, насколько нейтрально выглядит описание. Пока `target: null` — записи остаются `needs_target` и не обрабатываются.
