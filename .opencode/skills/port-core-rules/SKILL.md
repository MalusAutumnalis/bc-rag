# Перенос контента из core_rules в вики

## Расположение файлов (пути от корня репозитория bc-rag)

- Словарь терминов: `.opencode/skills/wh40k-to-fantasy/dictionary.yaml`
- Загрузчик JSON-записей: `ingest/json_source.py`
- Маппинг категорий на файлы вики: `.opencode/skills/port-core-rules/target_map.yaml`
- Очередь переноса: `.opencode/skills/port-core-rules/json_porting_queue.yaml`
- Исходный JSON с контентом книги: `data/core_rules/merged.json`
- Целевая вики: `../pathfinder-crusade-wiki/`
- Скрипт точечного поиска одной записи: `.opencode/skills/port-core-rules/scripts/find_entry.py`
- Скрипт пакетной подготовки черновика: `.opencode/skills/port-core-rules/scripts/batch_prepare.py`

## Жёсткие правила
- **НИКОГДА не редактировать файлы в `data/core_rules/`** — это read-only
  снимок исходной книги правил, эталон для сверки.
- Переносить только в файлы вики (`../pathfinder-crusade-wiki/`), никогда не
  в обратную сторону.
- Не переписывать существующий контент вики без явной команды — только
  **добавлять** недостающее. Если в вики уже есть раздел с тем же
  заголовком — не дублировать, а расширить его или пропустить, если он уже
  полный.
- Система "поклонение богу меняет цену/доступность таланта или навыка" в
  этой вики не используется. Поля `god`, `rivalGod`, `alliedTo`, `hostileTo`
  из JSON **никогда не переносятся** — ни как есть, ни в адаптированном
  виде. Из группирующих/классификационных полей остаются только `aptitude`
  (→ "Скл.:"), `level`, `requirements`.
- Никогда не создавать новые целевые файлы самостоятельно на своё
  усмотрение в пакетном режиме (см. ниже) — все целевые файлы созданы
  человеком заранее и прописаны в `target_map.yaml`. Если для записи нет
  цели — пропускать её (`needs_target`), не выдумывать файл.
- Для пакетной обработки использовать готовый `scripts/batch_prepare.py`,
  а не писать новые вспомогательные скрипты на лету (см. "Пакетная
  обработка" в Режиме 2).
  - Агент никогда не выполняет `git commit`. Изменения в вики оставляются
  в рабочем дереве для ручного просмотра и коммита человеком.

## Режим 1: точечный перенос раздела правил (текстовый md, не JSON)

1. Открыть `porting_map.yaml`, найти запись со статусом `not_started`
   для нужного файла (или создать новую запись, если её ещё нет).
2. Через `scripts/find_section.py` вытащить точный раздел(ы) из
   `data/core_rules/*.md` по `source_headings`.
3. Адаптировать текст:
   - заменить термины по `../wh40k-to-fantasy/dictionary.yaml` (инвариантные —
     точной заменой, склоняемые — с согласованием падежа/числа по контексту);
   - сохранить структуру: таблицы, разбивку на навыки/таланты/трейты как
     в оригинале, если в целевом файле уже есть похожая структура — влиться
     в неё, а не создавать вторую такую же секцию.
4. Вставить адаптированный текст в целевой файл вики на подходящее место.
5. Проверить на Chaos-маркеры (см. раздел "Chaos-маркеры" ниже) — при
   необходимости пометить `#Review` с кратким пояснением.
6. Обновить статус записи в `porting_map.yaml` на `done` или
   `needs_review`.
7. Оставить изменения незакоммиченными — коммит делает человек вручную,
   после просмотра diff.

### Когда НЕ переносить автоматически (режим 1)
- Разделы, целиком завязанные на технологический/sci-fi лор Warhammer
  40k без фэнтезийного аналога (импланты, стармтруперская техника и т.п.)
  — помечать в `porting_map.yaml` статусом `needs_review` с заметкой в
  `notes`, не переносить вслепую.

## Режим 2: пакетный перенос из JSON (skills/talents/traits/chems/instrument/gear/psychic_powers)

Используется для структурированного контента книги, для которого есть
чистый JSON вместо разобранного PDF. Категории и режим адаптации для
каждой — в `category_policy.yaml`. Категории `elite_archetypes`,
`implants`, `tech_powers`, `power_shield`, `steeds`, `ranged`, `melee`,
`armour`, `characteristics` в этом режиме не трогать (см. `exclude` в
`category_policy.yaml`).

### Предусловие
`json_porting_queue.yaml` должен существовать и быть сгенерирован из
актуального `target_map.yaml` (это делает человек через
`scripts/generate_json_queue.py` — агент этот шаг не выполняет
самостоятельно, потому что `target_map.yaml` заполняется вручную).

### Пакетная обработка

Для загрузки записей категории (или одного target-файла) используется
`scripts/batch_prepare.py`, а не написание нового скрипта на лету и не
последовательные вызовы `find_entry.py` по одной записи:

```
python scripts/batch_prepare.py <json> <category> [--target <файл>]
```

Скрипт выдаёт YAML, сгруппированный по `target`, с сырыми (НЕ
адаптированными) полями под шаблон категории — только записи со статусом
`not_started` и с заполненным `target` в очереди. `find_entry.py`
остаётся для точечной проверки одной конкретной записи (например, при
разборе `#Review` или уточнении спорного случая), не для основного потока.

### Шаги на один целевой файл

1. Получить черновик через `batch_prepare.py` для нужной категории (или
   конкретного `--target`, если ограничение задано в промпте).
2. Обрабатывать черновик **файл за файлом** (один `target` — один блок
   работы), не вперемешку между разными целевыми файлами.
3. Для каждой записи внутри текущего target-файла:
   a. Адаптировать текстовые поля (`description`, `effect`, `postEffect`,
      `action` и т.п. по списку из `ingest/json_source.py::_TEXT_FIELDS`)
      по `../wh40k-to-fantasy/dictionary.yaml` — инвариантные термины
      точной заменой, склоняемые — с согласованием падежа/числа по
      контексту предложения. Это выполняется моделью для каждой записи
      индивидуально, не regex-заменой.
   b. Не переносить `god`, `rivalGod`, `alliedTo`, `hostileTo` ни в каком
      виде.
   c. Оставить как есть (без адаптации, кроме числовых опечаток): `level`,
      `xpCost`, `requirements`, `action`, `range`, `sustain`, `aptitude`.
   d. Проверить на Chaos-маркеры (см. раздел ниже) — при необходимости
      добавить `#Review` с кратким пояснением, что именно нужно
      перепроверить человеку.
   e. Собрать финальный блок по шаблону категории (см. "Шаблоны вывода").
4. Вставить все собранные блоки в файл `target`, в логичное место (если в
   файле уже есть похожие записи — рядом с ними, не в конец без разбора).
5. Оставить изменения в рабочей директории незакоммиченными. Коммит
   делает человек вручную, после просмотра diff — агент НЕ вызывает
   `git commit`. Можно (но не обязательно) вывести в чат короткую сводку
   после завершения файла: сколько записей обработано, есть ли среди них
   `#Review`.
6. Обновить статус всех обработанных записей в `json_porting_queue.yaml`:
   `done` или `needs_review` (если поставлен `#Review`). Эти изменения
   тоже остаются незакоммиченными вместе с правками в целевом файле —
   коммитятся человеком за один раз.
7. Перейти к следующему target-файлу. Повторять автономно до отсутствия
   записей со статусом `not_started` в рамках текущего прогона —
   подтверждение на каждую единицу не требуется.

### Chaos-маркеры (проверка независимо от категории)

Ни `category`, ни `entryType`, ни `discipline` не гарантируют отсутствие
Chaos-специфичного контента внутри включённой категории. На шаге 3d
каждой записи проверять текст на прямые маркеры:
- упоминания конкретных Chaos-богов (Tzeentch/Nurgle/Khorne/Slaanesh или
  их русских имён) или эпитетов;
- ритуальная атрибутика поклонения (иконы, восьмеричная звезда,
  жертвенные символы);
- Cor (Порча) как механика;
- глубокий Imperium-лор (конкретные примархи, Империум, техно-физиология
  вроде "Второе Сердце космодесантника").

Если маркер найден — не пытаться самостоятельно "нейтрализовать" его
(например, просто заменить "Хаос" на нейтральное слово) — вставлять с
`#Review` и коротким пояснением, что именно завязано на Chaos/Imperium-лор.

### Автоматический #Review для WH40k-специфичных категорий талантов

Записи с `talents.category` из списка: `Geneseed`, `Skitarii`,
`Mechanicum`, `Technomystic` — если для них когда-либо появится `target`
в `target_map.yaml` (сейчас `null`, не переносятся) — помечаются `#Review`
на КАЖДОЙ записи независимо от того, насколько нейтрально выглядит
конкретное описание. Пока `target: null` — эти записи остаются
`needs_target` и не обрабатываются вообще.

### Шаблоны вывода

**talent** (ориентир — `iii продвижение/таланты/арсенал.md`):
```
###### {nameEn} / {name}
Уровень: {level}, Скл.: {aptitude через запятую}
Требования: {requirements через запятую, пусто — не писать строку}
{description}
```

**trait** (ориентир — `iii продвижение/трейты.md`):
```
###### {nameEn} / {name}
{description}
```

**skill**: аналогично trait, плюс строка характеристики:
```
###### {nameEn} / {name} ({characteristic})
{description}
Действие: {action}
```

**spell / psychic_power** (обязательно по `v магия/заклинания/spell template.md`):
вставляется в файл дисциплины (`v магия/заклинания/<дисциплина>.md`).

Если у записи есть `subdiscipline` и в файле ещё нет соответствующего
заголовка H4 — сначала создать его: `#### {subdiscipline}`. Если
`subdiscipline` текстуально совпадает с `discipline` (например,
"Эктомантия" внутри дисциплины "Эктомантия") — считать subdiscipline
отсутствующим, не создавать лишний заголовок. Если `subdiscipline`
отсутствует (`null`) — психосила вставляется на верхнем уровне файла, без
H4-обёртки, сразу как H6:
```
###### {nameEn} / {name}
**Требования:** {requirements через запятую}
**Действие:** {action}
**Поддержание:** {sustain}
**Психотест:** {psychotest}
**Дальность:** {range}
**Тип:** {powerType через запятую}
**Эффект:** {description}
```

**chem/gear/instrument**: свободная адаптация description + quality
(poor/good/best), без единого жёсткого шаблона — сохранять деление на
абзацы как в исходнике.

### Что НЕ делать в пакетном режиме
- Не переносить `god`/`rivalGod`/`alliedTo`/`hostileTo`.
- Не создавать новые файлы вики.
- Не пытаться сгруппировать записи "по смыслу" мимо `target_map.yaml` —
  группировка уже задана через `category`/`discipline`/`gearType+entryType`
  человеком.
- Не удалять и не переписывать теги `#Review`, оставленные в предыдущих
  проходах, пока человек их не снимет явно.
- Не вызывать `git commit` вообще, ни на запись, ни на файл — только
  `git add`, если это явно попросят, либо вообще не трогать git.
  Коммит всегда делает человек.
- Не изобретать новые сокращения терминов, которых нет в
  `../wh40k-to-fantasy/dictionary.yaml` — предложить добавление, не
  переводить на лету.
- Не писать новые вспомогательные скрипты для загрузки/группировки данных
  — использовать `scripts/batch_prepare.py`.
- Не адаптировать термины или проверять Chaos-маркеры regex/keyword-скриптом
  — это выполняется моделью для каждой записи индивидуально.
